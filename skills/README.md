The current Director guidance is **release 8.0.2** ([skills/v8.0.2](v8.0.2/release.json)) with JSON tool contract `7.0.0`. New films lock it, and saved V7, 8.0.0 and 8.0.1 films move to it on their next eligible fresh native turn. Release 8.0.0 ([skills/v8](v8/release.json)) and historical V1–V7 package bytes remain available for verifying existing immutable locks.

8.0.1 changes four packages (`production`, `plan-authoring`, `craft-shot-prompting` and `craft-visual-style`, historically labelled `8.1.0`); the other 18 are byte-identical to 8.0.0. It says propose, wait for the person to accept, then make keyframes (the application refuses an early `make_keyframes` with `PROPOSAL_PENDING`), and it merges the references a new film reads at intake: shared planning into `production` `references/routing.md`, the creative-patch example into `plan-authoring` `references/grammar.md`, keyframe and motion prompts into `craft-shot-prompting` `references/prompts.md`, and the style library and record into `craft-visual-style` `references/looks.md`. The first turn of a 20 s IG skit now reads 13 distinct files instead of 17 (plus four free repeats).

A release pins 22 instruction-only packages with one `release.json`. The application routes them from the saved `project.filmKind`: core always, the film's type package, the vertical format package for 9:16 films, and the craft packages those need (some only when the film has characters, a soundtrack or narration). Only routed `SKILL.md` entries and the two core references are injected; every other file is read on demand with `read_guidance`: up to 32 distinct files and 192 KiB per Director turn, with repeats of a file already read that turn free (up to 32). The allowance starts again with the next message; past it, `GUIDANCE_READ_LIMIT` says what was used and tells the Director to continue with what it has.

Every `filmKind.kind` routes to its type package; `undecided` and `other` use the fallback (core plus story, visual style and shot prompting). Permissions and decisions are written only in core; a CI lint keeps them out of the other packages, and a CI budget keeps entries and the worst-case injection within `release.json` limits.

A shipped package, release and tool catalog are never edited in place. This includes the root `production` and `plan-authoring` packages, `v2` through `v8`, `v8.0.1`, `v8.0.2`, and catalogs `1.0.0` through `7.0.0`. Every later guidance or schema change ships through the release command below. A changed package receives the release version; unchanged packages retain their previous versions and exact bytes. The frozen runtime `SHIPPED_DIRECTOR_RELEASES` table loads append-only rows from `skills/shipped-releases.json`. A release `N.0.0` lives in `skills/vN`; every later release of that major is a complete new directory named by its full version (`skills/v8.0.1`), so the loader's one-directory-per-release rule holds and earlier directories stay untouched. Package, release and catalog digest tests pin that history; do not update a historical pin to accommodate an edit.

OpenSlate validates exact package contents, creates immutable content-addressed snapshots, locks compatible versions and records activation and every guidance read. Already-started epochs keep their saved lock. Skills supply instructions; typed tools enforce current project inputs, scope and exact media review. Configured provider credentials require no separate API-key approval or usage allowance.

These are OpenSlate product packages; they are not installed into a contributor's global Codex configuration. See the [skill and tool framework](../docs/technical/SKILLS-TOOLS.md), the [v8 architecture](../docs/ai/skill-architecture/2026-10-28-skill-architecture.md) and the [film-kind taxonomy](../docs/ai/film-kind/2026-10-28-film-kind-taxonomy.md).

## Author and release guidance

1. Run `pnpm skills:draft`. It validates shipped releases and copies the latest one into `skills/next/`, the only editable guidance working copy. It refuses if a draft already exists.
2. Edit `skills/next/**`. Leave manifest versions and package digests alone: the release command computes them. When adding/removing packages or changing routing, edit the draft `release.json` package list and metadata as well.
3. Run `pnpm skills:release --note "Describe the change"`. Patch is the default; use `--minor` or `--major` for a larger release, and `--contract x.y.z` to select a supported new tool contract. Contract selection updates package compatibility before comparison. The command refuses no-content-change releases, version collisions and existing target directories. It stages and validates the complete release before publishing the directory and appending the JSON row; historical row text stays intact. A failed publication restores the draft.
4. Run `pnpm skills:check` and the normal test gate. `pnpm test` includes the integrity checker. Every shipped release must also construct the exact Director stage-prompt lock, fit its word budgets, and keep permission/decision calls out of non-core packages. A leftover `skills/next/` fails checks; during local authoring, `OPENSLATE_SKILLS_DRAFT=1 pnpm skills:check` (or `pnpm test`) permits it and names the override in the check message. Finish the draft before merging.

A package's version is the release in which its content last changed. Content comparison ignores only its manifest's version value; all other manifest formatting and declared file bytes count. Unchanged packages preserve the exact previous manifest and digest, including across a major release. Release-only metadata changes keep every package version. A major `N.0.0` release uses `skills/vN`, matching `releaseDirectory`; later releases use `skills/v<version>`.

Release **8.0.2** is the single version-only exception, produced with `pnpm skills:release --realign`. It has identical instruction content to 8.0.1: `production`, `plan-authoring`, `craft-shot-prompting` and `craft-visual-style` are aligned to `8.0.1`, and the other eighteen retain `8.0.0` and their original digests. The row records `realign: true`. This flag refuses content changes, another release version or a second repair. Historical `skills/v8` and `skills/v8.0.1` remain byte-identical.

Parallel authors each use their own worktree and their own `skills/next/`. Whoever merges second re-creates their draft from the merged latest release, reapplies their content edits and re-runs `pnpm skills:release` on top of the first. Never resolve a collision by overwriting a shipped directory or editing an earlier row. Each worktree's authoring commands also hold an exclusive `skills/.release-lock`; after a crash, inspect the draft, row file and any unregistered release directory before removing a stale lock. The checker fails on unregistered release directories rather than adopting them.
