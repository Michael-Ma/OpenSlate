# Storyboard edits, narration fit, timeline, export, and the views not yet designed

**Conclusion: the Keyframes view's narration-fit and edit flows can be drawn today, but four server behaviours make them unsafe or wrong in practice.** Each one needs a server change before or alongside the web work.

1. **Every hand edit opens a new Director request.** Every storyboard command calls `beginRequest(editing:true)` (storyboard.ts:393-405). That request supersedes active requests, revokes every Director epoch and places a hold (service.ts:127-132). Holds stop queued jobs from running (engine.ts:755-770) and block export (application.ts `assertUnpaused`). A shot's narration session does the same (narration-scope.ts `createShotNarrationSession`).
   - So "Make 2.3 8 s" kills a running Director turn.
   - A music or reorder tweak holds the whole film until a later request picks it up.
2. **Undo throws away paid media.** Undo works only on the latest edit, and only while nothing else has changed the project (storyboard.ts:341-358). When it runs, it also detaches the shot's keyframe and video, because the per-field exceptions that keep a keyframe alive on a duration edit do not apply to undo (storyboard.ts:439-470). Narration accept has no undo at all.
3. **Voice lines are only measured at video time, by the browser.** Today speech is made only inside the browser-run scene confirmation (scene-confirmation-model.ts:249-528), or one shot at a time from the narration panel. The design needs every voice line's length at keyframe review, so the server needs one "make keyframes and voice lines" command.
4. **Export needs a timeline written by the Director.**
   - Export needs a render node, and only Director plan source or the demo creates one (planning/index.ts:283-308). Scene composition only preserves an existing one (scene-composition.ts:322-333).
   - Export plays shots in the plan's order, not the storyboard's (timeline-capture.ts:103-116).
   - Demo media is refused at export (timeline-capture.ts:157-161).

**Already supported, with caveats:**
- **Keep 6 s:** accept the take with a trimmed range in keep mode (shot-audio-routes.ts:735-749).
- **Make 8 s before any video exists:** this is free. A duration edit leaves the keyframe in place (storyboard.ts:455-459) and the keyframe check ignores duration (planning/index.ts:86).

**Where the design or the research is wrong against the code:**
- Motion and duration edits make only the video out of date, not the keyframe.
- Editing one shot clears only that shot's video, not the whole scene's.
- An edited narration line cannot "resolve" a note until new paid speech has been made and measured.
- Accepting with "match the shot to the recording" sets the exact recording length in frames, not whole seconds.
- The browser's "opened" record includes the project revision (conversation-actions-model.ts:68-76), so any free edit resets every frame to Not opened.
- Shortening a shot below its accepted narration is allowed. It then breaks narration playback for the whole film (audio-placement.ts:17-21 via shot-audio-routes.ts:843).

**Server gaps for the views not yet designed:**
- Plan: Brief, Story and scene-direction edits detach paid media for no reason (storyboard.ts:114-121, 444). Scenes have no title, delete or reorder.
- Projects: there is no rename, delete or duplicate route.
- Assets: the library lists only images and videos, with generic labels and no link to a shot.
- Music and narration takes share one audio library.
- Settings: there is no project default voice.
- Personal voice: the web has no control to ask for it on a shot.
- Prices: only a flat, host-configured estimate per attempt exists (provider-catalog.ts:207).

## SB-1 Direct storyboard edits revoke the Director, supersede requests and place holds that block jobs and export [server, L, compatible_today=False, deps=]
- Design: Make 2.3 8 s / Keep 6 s / Edit narration / inspector edits as free, instant actions with a toast and Undo while the Director keeps working
- Current: Every storyboard command calls s.beginRequest(projectId,'local-user',...,{editing:true,scopeIds}) (apps/server/src/storyboard.ts:393-405). beginRequest supersedes every active editing request, revokes every Director epoch and calls engine.setHold for each scope (apps/server/src/application/service.ts:127-132). Global kinds (addScene, addShot, deleteShot, moveShot, soundtrack, treatment, undo) hold the whole project (storyboard.ts:385-392). Holds stop dispatch of image, video and speech jobs in that shot, scene or project (apps/server/src/execution/engine.ts:755-770) and make export fail with MEDIA_HELD (apps/server/src/media/application.ts assertUnpaused; target.scopeIds always contains projectId, timeline-capture.ts:121). Holds are released only by a continuation request (service.ts:133-142), by scene generation (scene-generation.ts:604-650), by a plan apply from the owner (service.ts:565-572), or by narration rebase (canonical.ts:203). Shot narration sessions do the same thing (narration-scope.ts createShotNarrationSession → beginRequest editing:true, scope [shotId]).
- Gap: The design treats these edits as free and harmless. Today one click ends a running Director turn. It can hold that shot's queued keyframe job (or every job, for a music, reorder or add edit), and it can block export until a later Director request picks the edit up. The UI has no way to release a hold.
- Change: server: add a 'direct edit' path to editStoryboard. When an edit detaches no in-flight attempt, (a) record the message with editing:false-like semantics, so the Director is not revoked and other requests are not superseded, and (b) place no hold. Shot-scoped edits that do outdate queued work get a hold that is released at commit. Leave soundtrack, moveShot and addScene/addShot hold-free. Change storyboard.ts:385-405 and service.beginRequest options (new flag, e.g. directEdit:true). web: remove the composer's 'continue saved edit' state once holds no longer outlive the edit.
- Risk: Holds currently protect a Director turn from publishing a plan built on a stale storyboard. Instead of revoking the turn, the Director's prepare/apply must keep rejecting on headVersion (it already checks before.headVersion === prepared.baseVersion, service.ts:538). Test that a stale Director apply still fails. Ship behind a capability flag and keep old behaviour for edits made while an attempt is running.
- Tests: Server unit (storyboard.test.mjs): a duration edit with no video does not change epoch state, places no hold, and a queued keyframe job for another shot still dispatches. Integration: a Director apply prepared before the edit fails with REVISION_CONFLICT. Export after a music edit is not MEDIA_HELD.

## SB-2 'Make shot N s' must be one command: lengthen the shot and accept the voice line [server, M, compatible_today=False, deps=SB-1,SB-5]
- Design: Banner choice 'Make 2.3 8 s' (free before video; updates film length and later scenes' start times)
- Current: The duration edit is storyboard {kind:'shot',field:'desiredFrames'}, 90-450 frames (storyboard.ts:167-174). It keeps the keyframe (image bindings excluded at storyboard.ts:455-459; image intent ignores desiredFrames, packages/core/src/planning/index.ts:84-86) but detaches the video and timeline/render bindings. The measured take is not accepted, so the shot stays narrationPending and video stays blocked (scene-generation.ts:509-518 TIMING_REQUIRED). Accepting takes a separate shot session plus POST .../accept (shot-audio-routes.ts:657-823), which needs the head version that the edit just changed. durationMode match_audio sets desiredFrames to the exact cue frames, not whole seconds (canonical.ts:87). The browser chain always uses keep with the full range and throws NARRATION_CUE_OUT_OF_RANGE (apps/web/src/scene-confirmation-model.ts:495-523). The video length is rounded up to whole seconds and must be no more than the model's maxFrames (packages/core/src/planning/scene-composition.ts:158-182), so 8 s can be refused by the selected video model. Film length and later start times are pure derivations from storyboard order (narration/audio-placement.ts:9-12).
- Gap: The design's one-click choice is two or three requests today, each a new editing request with its own head-version and request fences. It cannot be undone as one action, and nothing checks the video model's maximum length.
- Change: server: new POST /api/projects/:p/scenes/:s/narration-fit {shotId, choice:'extend', seconds, expectedHeadVersion, takeId, takeSha256}. In one transaction it sets desiredFrames=seconds*30, checks seconds against the video profile maxFrames and the 360 s film cap (storyboard.ts:366-372), and runs the narration accept chain (recordHumanCue/place/accept/acceptAudio/prepare/apply) with keep and the full range. Return a decision record id for undo (SB-9). core: pure fitOptions(shotFrames, takeSamples, profile) → {extendTo, trimAt, fits}. web: banner action calls it and recomputes the timeline from storyboard order.
- Risk: Accept runs async artifact verification outside the transaction (canonical.ts:131-158), so 'one transaction' must be prepare + apply with a durable decision record. On partial failure, keep the duration and leave narration pending. Never spend money in this command.
- Tests: Unit: fitOptions table tests (7.4 s take, 6 s shot → extend 8 s / trim at 6 s; model max 6 s → extend unavailable). Server integration: narration-fit extend leaves the keyframe binding intact, sets cue within_shot, scene view row narrationPending=false. Browser: banner timeline after the action shows Scene 3 starting 2 s later.

## SB-4 'Edit narration' can only estimate length; measuring means paid speech again [web, S, compatible_today=True, deps=SB-5,SB-11]
- Design: Edit narration inline with a live length estimate; saving a line that fits resolves the note
- Current: A storyboard narration text edit sets narrationPending=true when the writing changes (storyboard.ts:262-269). It keeps the keyframe, and the video too when the cue is within_shot, because shotIntentDigest drops the cue for within_shot (planning/index.ts:86). The only real length comes from POST .../narration/shots/:shotId/generate (shot-audio-routes.ts:364-539), which is paid, needs a configured speech profile and no stop in force, and defaults the voice to 'cedar' (line 455). Text plus instructions is capped at 1,792 bytes (narration-speech-service.ts NARRATION_SPEECH_SPLIT_REQUIRED). The prototype's 0.55 s/word estimate is invented (DESIGN.md deviation 6). The server has no estimator.
- Gap: The design resolves the note when the line is saved. In the real app the note can only move to 'waiting for a new voice line (about $X)', and it resolves only when the new take is measured and fits.
- Change: core: pure estimateSpeechSeconds(text, language), with separate rates for English words and Chinese characters, and byte-limit validation; label it as an estimate. web: Edit narration saves through storyboard {kind:'narration',field:'text'}, then offers 'Make voice line · about $X' (SB-11), which calls the voice-line command (SB-5). The note shows Waiting until the take is measured. The old take stays selectable in the take list.
- Risk: Estimates mislead. Always show 'estimate' and never auto-accept on an estimate. Never call generate without an explicit priced press.
- Tests: Unit: estimator table tests (EN and zh, byte-limit edge). Web model test: after a text save the note state is 'waiting_voice', not resolved. Server existing: a text edit sets narrationPending.

## SB-5 Voice lines must be made with the keyframes, by the server, so their lengths are known at review [server, XL, compatible_today=False, deps=SB-1,SB-11]
- Design: Narration lengths known at keyframe review time (note b: 'Narration 7.4 s, shot 6 s')
- Current: Keyframe generation composes image operations only (scene-generation.ts:539-571, kind image). That supersedes the other shots' sessions and holds the shot, which blocks the same shot's queued image job; only the speech node is exempt (engine.ts:766-768, narration-scope.ts narrationSpeechHoldExemption). Once a take exists, GET /scenes/:id/generation already returns its length (timing.durationFrames) and an over-length error (apps/server/src/scene-narration-view.ts:150-185).
- Gap: There is no single press that makes keyframes and voice lines together. Doing it per shot today breaks other shots' sessions and holds their keyframe jobs. Closing the tab strands paid speech (earlier finding 1.4).
- Change: server: extend POST /scenes/:id/generate kind 'image' with includeVoice:true (or add a new kind 'keyframes_and_voice'). The view adds narration.state: none|making|fits|too_long|unknown, measured seconds and price. Scene video then needs no browser chain; delete the speech steps from scene-confirmation-model.ts.
- Risk: Paid speech starts on the keyframe press, so the price must include voice lines (SB-11). Accepting automatically writes a canonical narration commit; keep the existing exact-take identity and idempotency so a retry never pays twice. Migration: projects with a pending browser checkpoint must still resolve through the old steps.
- Tests: Server integration with the fake speech provider: one press creates N image and M speech attempts, takes bind and accept when they fit, a too-long take reports too_long, a replay with the same key creates no new attempts. Restart mid-job resumes. Web: the scene view shows measured lengths before any video.
