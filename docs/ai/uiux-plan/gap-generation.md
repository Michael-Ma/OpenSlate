# Generation, review and job state

**Verdict.** Today's routes can already make keyframes for a whole scene or for chosen shots, regenerate one shot's keyframe as a new paid take, and make a scene's clips from exact keyframe bytes. That covers Scene 3 "Make 2 keyframes" and "Regenerate 2.2". Most of the rest of the Keyframes design cannot be built on the current backend as it stands:

- **Confirm.** Scene confirmation is still a 597-line browser saga with localStorage checkpoints and Web Locks (`scene-confirmation-model.ts`). The `/confirm` path it targets exists only in the browser.
- **Per-frame "Opened".** It is kept in React memory and keyed by the project `revisionId`, so any edit anywhere in the film, or a reload, clears it (`App.tsx:393,1034-1062`).
- **Status reads.** There is no read that rolls status up across the project. The pills need one `/generation` GET per scene, and each GET builds the full snapshot and re-hashes every keyframe. The browser also works out "keyframe current / video saved" a second time, under different rules (`project-results-model.ts:28-35` vs `scene-generation.ts:124-206`).
- **Price.** No figure is attached to a scene or a shot. The engine reserves the capability lock's `unitCostMicros` once per attempt, so each automatic retry costs again.
- **States the scene view cannot show:**
  - "failed" and "never made" look the same.
  - "queued", "held by an edit" and "stopped" are mixed together (`candidatePending`, `scene-generation.ts:225-230`).
  - "outdated" shows as an empty frame.
  - "no answer" from the provider blocks the shot, the scene's whole video command and that model's capacity on every film. No route lets the user give up on it.
- **Stop.** Stop leaves unsent jobs bound, so they go out on resume without a new confirmation. The server has `resume`, but the UI never calls it.
- **Synthetic messages.** Every paid press writes a fake user message into the conversation.
- **Project-wide busy flag.** Any open Director question blocks every press. That collides with the banner's Regenerate 2.2 while note (b) is still open.

**Where the research files are wrong:**
- `GET P/review` is not unused. The web fetches it on every snapshot change (`App.tsx:180-186`), and the GET writes a `review_snapshot` row (`app.ts:254-258`, `engine.ts:275-311`).
- An outdated take is not "only in P/assets". The attempt history in the snapshot already lets the web show "Earlier keyframe" (`project-results-model.ts:41-52`).
- A stop is not lifted only by a `resumeFromStopId` message. `POST controls {action:"resume"}` exists (`service.ts:654-668`).
- Queued shows as pending only when no hold covers the scene.
- Whole-scene generate does not require an `Idempotency-Key`: the server mints a fresh id when the header is missing (`scene-generation.ts:397-398`).

**Recommended order:**
1. Mark presses as non-messages and require an idempotency key (small, can ship at once).
2. A generation overview read that also carries the price.
3. A durable Opened record.
4. The server-side confirm command.
5. Give-up for a job with no answer.
6. Stop that detaches unsent jobs, plus Continue.
7. Then delete the browser saga.

## GR-4 Narration length is only known after paid speech; overflow policy at confirm [server, M, compatible_today=False, deps=GR-3]
- Design: Note (b) 'Narration 7.4 s, shot 6 s' with Make 2.3 8 s / Keep 6 s (cut) / Edit narration, settled before confirm
- Current: A too-long line is found only after speech is bought. The saga throws NARRATION_CUE_OUT_OF_RANGE after paying (scene-confirmation-model.ts:501-509), and the view reports it only when a recording already exists (scene-narration-view.ts:136-151). The accept route already supports trimming (startSample/endSample) and durationMode keep|match_audio (narration/shot-audio-routes.ts:657-700). The saga always accepts the full length with durationMode 'keep' (scene-confirmation-model.ts:495-523). No text-based length estimate exists on the server.
- Gap: The design shows the 7.4 s overrun before the user pays for video. On today's flow that needs the voice line made first, and 'Keep 6 s, cut the line' has no command.
- Change: server: the confirm command takes a per-shot narrationPolicy {fit: 'cut_to_shot'|'extend_shot'|'block'} that the runner turns into endSample = shot length, or durationMode 'match_audio'. Changing the shot length voids the video recipe, so 'extend_shot' must run before the video step is approved. Recommended product rule: voice lines are made with the keyframes (a separate paid press) so their length is known before the confirm; the confirm then buys no speech. The overview carries narration {measuredSeconds, plannedSeconds, fits}.
- Risk: Money: speech bought and then wasted when it overruns. Integrity: 'extend_shot' changes durationFrames and so the video price and approval; it must re-quote. Belongs partly to the audio area; coordinate with it.
- Tests: Integration: a 7.4 s fake speech on a 6 s shot under each policy (cut gives a 6 s cue and video proceeds; extend gives 240 frames and a re-quote; block stops before video). Unit: policy to accept-body mapping.
